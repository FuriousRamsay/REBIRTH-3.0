## Foundation identities, transitions and durable boundary

Stable IDs parse fixed32hex nonzero values or originate from GUID. Profiles are immutable and validate ownership/order/respawn capability dependencies; built-ins initialize under reentrant lock with volatile publication. State revision wraps unchecked uint and Dirty records mutation; projections clone state. Transition functions validate enums/finite guard coordinates/capability and explicit presence/travel matrix. Removed is terminal for changes, same-state SetPresence succeeds idempotently. Work order and current work state are release-gated. These transactions validate domain state, not user authorization; Entity methods require server and command submission delegates issuer/revision authorization to Gateway.

Binary persistence magicRBNP/schema4 writes stable/profile/ownership/presence/order/travel/optional finite guard/revision/appearance. Reader accepts schema1–4 with legacy defaults, validates enum/guard domains and marks reconstructed state clean. Write deliberately does not clear Dirty: serialization is not a durable acknowledgement. Stream boundedness, profile/owner cross-validation, publication and recovery remain enclosing persistence owners' responsibilities. No native stream replay or new persistence test performed.

Runtime registry keeps native-ID and stable-ID maps under lock, refuses duplicate stable identity, clones sorted snapshots, and returns existing native-ID registration unchanged. Rebind rejects an occupied stable identity; unregister removes maps and cancels command/activity/recovery/lease state. World lifecycle reset invokes ClearForWorldChange at Lifecycle446/508. Register/rebind correctness therefore depends on native lifecycle removal and authenticated reconstruction callers, not an identity chosen by a network client. Registry TryGet exposes the live state object intentionally; server/main-thread mutation ownership is external to its dictionary lock.

Bootstrap RebirthFresh_Init73 initializes FoundationService; Entity.Init also ensures initialization. Service registers lifecycle/presentation and game start callbacks once, deferring XML authoring validation until GameStartDone. Validation errors log and mark validation complete; this is diagnostics, not proof that an invalid class cannot spawn. Native event ordering is an established dependency, not newly extracted here.
