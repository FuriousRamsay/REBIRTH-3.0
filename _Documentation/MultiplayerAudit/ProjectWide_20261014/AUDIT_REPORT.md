## Findings and investigations

### MP-025 — Farming diagnostic sessions are not isolated by requester

Classification: source-confirmed diagnostic integrity defect in Debug; Release falsely acknowledges unavailable diagnostics. Gameplay mutation is not established.

The crop diagnostic request authenticates actor and bounds its center, but accepts a client-supplied session ID. AdvancedFarmingCropGrowthDiagnosticService.Start removes the requester's prior session, then inserts under MakeSessionKey(sessionId, role), which omits requester identity. Two requesters choosing the same ID and SERVER role overwrite one another's session. Every accepted Start also immediately samples and clears shared light/temperature/hover caches; repeated requests have no handler cooldown despite one-session-per-requester replacement. Normal generated IDs include entity ID, but the packet does not require that format. Release Start returns unavailable while the handler sends accepted=true.

Correction after checkpoint: scope diagnostic identity to authenticated requester/session, bound and normalize labels, limit repeated starts, and report actual admission/availability. Preserve usable paired diagnostic correlation. Tests must distinguish same-process HOST/SERVER labels from independent multiplayer peers. See FARMING_TRACE.md. Packet framing/allocation limits remain separately pending; no unbounded-allocation exploit is claimed here.

### MP-024 — Farming water exchanges do not verify item publication before settlement

Classification: source-confirmed conservation/failure-handling gap in local and remote paths; actual gameplay incidence not measured.

The configured CollectWaterRebirth, DumpWaterRebirth and ExchangeItemRebirth local paths change tank water before calling a void held-item replacement helper. The server request path reverses the order and catches exceptions, but also never checks the slot postimage. A nonthrowing refused Inventory.SetItem therefore allows water settlement without the corresponding container conversion. Existing owner-hold patches provide a setter-suppression mechanism; overlapping action reachability and native remote inventory replication still need validation. See FARMING_TRACE.md for bindings, authorization checks and limitations.

Correction after audit/checkpoint: settle the original water action with exact before/after item and tank images, verified publication and recoverable outcomes, preserving native owner action semantics. Do not rely on exception-only rollback or an unconditional server inventory rewrite. Cover refused writes, slot changes, simultaneous players, retries and shared reload conservation.

### MP-023 — Workstation security save retries can overwrite the last usable backup

Classification: source-confirmed persistence failure window; host/dedicated ownership and lock records. No current corruption or unauthorized access demonstrated.

`RebirthWorkstationSecurityService.Save` copies the primary over `.bak`, then creates/truncates the primary and writes directly. If writing fails after truncation, dirty is restored; the next retry copies the damaged primary over the previously good backup before writing again. Load ignores a surviving backup when the primary is absent. Failed primary/backup recovery has no explicit write quarantine. Missing records can subsequently enter GetOrMigrateState's land-claim-based ownership migration, so preserving security records matters beyond cosmetic state.

Correction after audit/checkpoint: write and validate a complete temporary candidate before durable publication; preserve recovery candidates across failed attempts; try backup for missing primary and distinguish failed recovery from a new store. Preserve SdFile/platform requirements when selecting publication implementation. Validate with failure injection at copy/create/write/publication and grouped ownership/lock reload checks.

### MP-022 — Packed-container restore consumes receipt before recoverable publication

Classification: source-confirmed interruption/retry gap; authoritative host placement, including remote-player placement. Runtime incidence not measured.

`RebirthContainerPackUp.Restore` renames the issued token to `.placed` before resizing/publishing contents and restoring settings. Any later exception or process termination leaves a consumed token; the same method returns on retry because the original path no longer exists. Retained JSON preserves the contents for manual recovery but contains no destination/phase/save witness enabling automatic settlement. See PACKED_CONTAINER_TRACE.md for authority, grant and placement tracing.

Correction after audit/checkpoint: journal the original destination and restoration phases, distinguish reserved from durably applied, and recover without publishing twice. Do not simply move the rename later, which would create a duplicate-publication window. Add injected-failure coverage and grouped save/reload verification.

### MP-021 — Failed fire-state recovery remains writable

Classification: source-confirmed persistence recovery gap on authoritative hosts; triggered by unreadable/unsupported primary and no usable backup. No current save corruption asserted.

Evidence: `RebirthFirePersistence.Load`, `LoadFile`, `UpdateAutosave`, `Save`, and `RebirthFireModApi.OnGameStarting/OnWorldShuttingDown` in RebirthFireSystem.cs. Startup clears service state and resets lastSavedRevision to -1. If primary and backup cannot load, Load logs and returns without a failed-load state or write quarantine. The next autosave or shutdown can publish the empty/new session state over the original primary. File.Replace then replaces the backup as well, potentially eliminating the previous recovery candidates. Unsupported-version files take the same path.

The writer flushes its temporary file and uses RebirthDurableFileCommit, which correctly avoids delete-before-move. The defect is permission to publish after failed recovery, not that publication helper. The loader also correctly tries a backup when the primary is missing and constructs parsed collections before Restore.

Correction after checkpoint: distinguish new/no-save sessions from failed recovery; preserve failed candidates and prevent overwriting them until an explicit, validated recovery policy succeeds. Keep transient runtime fire operation separate from authority to replace unresolved saved state. Cover corrupt/missing/unsupported primary and backup combinations and shutdown after failed load in offline fault cases before the grouped reload test.

### MP-020 — Fire snapshot replay does not preserve ordering within a delta batch

Classification: source-confirmed ordering gap in remote visual recovery; runtime incidence unmeasured. This affects projected fire/smoke state, not demonstrated authoritative fire loss.

Evidence: `RebirthFireSystem.QueueDelta/FlushDeltas` sends multiple ordered transitions with one final batch revision. `RebirthFireVisualManager.ApplyDelta` buffers them during snapshot assembly. Both snapshot commit and AbortPendingSnapshot sort the buffered list using only revision, without a stable ordinal or per-entry sequence. Equal-revision transitions for one position can consequently replay out of order. The normal direct application path preserves list order.

Correction after the audit/checkpoint: preserve source order within equal-revision batches during buffered replay, including abort and snapshot replacement paths. Add a deterministic regression covering add then extinguish/remove at the same coordinate with intervening entries and snapshot completion/timeout; then verify authoritative and remote projections in the grouped multiplayer batch. See FIRE_TRACE.md.

### MP-001 — Quick Stack category response can reopen or retarget stale UI

### MP-004 — Bootstrap records failed fire integration as completed

### MP-007 — Consumption can leave an unreconciled owner debit

Classification: source-confirmed recovery gap; high priority for reported remote food behavior. Actual item duplication/loss is not yet demonstrated in-game.

Trace: ItemActionConsumeMetabolismRebirth.Dispatch sends type/seed/autoSip without an original operation ID or source-slot hold. NetPackageRebirthMetabolismConsumeRequest finds a matching server-side stack, executes consumption, then sends one publication. RebirthConsumptionOwnerPublication.Apply refuses a changed source preimage to avoid overwriting another item. That refusal is safe locally but does not reconcile the already accepted ingestion/debit. An owner moving/changing the source before the reply, or a disconnect between consumption and publication, therefore has no integrated settlement path in this flow. The request also has no operation identity for distinguishing a replay from a second intentional serving. A fix must bind the original source and operation, retain a recoverable outcome and apply effects once. Merely enabling the dormant retry flag would not close the cross-repository durability or moved-source gap. Preserve the accepted original native action boundary and do not blindly overwrite a whole inventory.

### MP-008 — Remote-resource refunds can discard unplaced items

Classification: source-confirmed loss path; high severity when an accepted remote preflight cannot complete and both owner inventories cannot accept its refund.

Evidence: Scripts/Crafting/RemoteCrafting/RemoteResourceClientTransactions.cs, ReceiveResult and RefundRemoteToLocal (around 394–552 and 665–680).

ReceiveResult removes its pending lease before resuming or refunding the action. RefundRemoteToLocal clones each removed stack, attempts belt then bag placement, and only logs a warning if placement fails. It retains no remainder for retry, then logs that resources were refunded. The server has already removed those resources. The separate RemoteResourceRefundProducer explicitly says preparation-only and has no production callers. Correctly retain exact remainder and an original-operation settlement before releasing the lease; do not silently drop, recreate the original whole stack after a partial placement, or introduce an unrequested world-drop fallback.

### MP-009 — Remote-resource outcome journal can forget unresolved removals

Classification: source-confirmed lifecycle gap; high-priority disconnect/save/reload and sustained-load qualification.

RemoteResourceTransactionOutcomeJournal is memory-only. It evicts oldest entries above 2,048 without distinguishing settled/acknowledged delivery and clears on world unload. The client Clear discards all pending leases and advances its epoch. QueryOnly returns Unknown for an evicted outcome and UpdatePendingTransactions keeps querying. Thus a server-confirmed removal may become unrecoverable by this protocol before the owner has applied its grant/refund, and eviction can leave a live pending client querying indefinitely. Preserve original outcomes durably until acknowledged; bound admission rather than evict unresolved custody. Runtime reproduction must distinguish this from the more recent station-specific durable journals.

### MP-010 — Cooking pull has no delivery retry or scoped callback retirement

Classification: source-confirmed availability/recovery gap; high priority for remote ingredient pulls.

RebirthCookingPull stores a callback in a static waiting dictionary, sends once, and removes the callback before invoking it on a matching response ID. There is no query/retry pump or teardown/rebind policy in this service. IDs start at UTC ticks, reducing restarted-client collision risk, and the server uses the removal outcome journal, but neither feature delivers an outcome after disconnect. A send exception deliberately retains the callback yet there is no producer that retries it. The UI can remain collecting ingredients while the host has already withdrawn them.

XUiC_RebirthCookingWorkspace.CompleteIngredientPull correctly prevents changed UI selections from receiving ingredients, but its fallback returns items through the captured xui.PlayerInventory before checking that the original session remains current. NetPackageRebirthCookingPulled only checks IsRemote, not current world/player/session. Audit fix must retain original owner custody, bind delivery to that owner/world, and settle closed-window receipts without treating window closure as permission to forget them. Do not clear the dictionary as a cosmetic leak fix: that would erase unresolved withdrawals.

### MP-014 — Bridge health polling permanently increments outstanding-request accounting

Confirmed source defect in test infrastructure. `Scripts/GameBridge/RebirthGameBridge.cs`, `HandleContext`, creates `BridgeRequest.From` before checking `/ping`. `From` increments static `open`, but the ping branch answers directly without `Complete` or `Abandon`, so every successful health poll leaves one outstanding request. `RebirthGameBridgeCombat.GuardTick` uses `OpenCount == 0` to admit the downtime agenda; that agenda can remain suppressed after the first ping. ### MP-015 — Native workstation completion loses deferred awards and post-award effects

Source-confirmed recovery gaps; runtime reproduction pending. `RebirthWorkstationCraftCompletion.After` ignores a failed local `Credit`; remote completion sends one notice without an acknowledgement/retry producer. ### MP-016 — Camper update rereads and hashes the entire energy transfer history

Confirmed source performance defect; runtime cost not measured. `RebirthCamperEnergyVehicleTick` runs after each authoritative `EntityVehicle.Update`. `RebirthCamperEnergyRuntime.Tick` invokes `CustodyReady` before the configured energy cadence check. The installed delegate calls `RebirthCamperEnergyCustody.Ready`, which constructs the journal and calls `FindPending`. `FindPending` enumerates every prepared receipt in the save's energy journal and calls `Read` on each operation before filtering by vehicle. `Read` loads and hashes the full snapshots for every existing phase. Applied history is retained, so work grows with all historical transfers and is repeated for each loaded camper on the main thread, even when no transfer is pending.

Keep the durable journal as authority, but load and validate a world-scoped index at recovery and synchronously update/invalidate it on journal publication. Cache only verified state, maintain per-vehicle unresolved lookup, and refuse resources when recovery is uncertain. Merely delaying the safety gate until after resource mutation or deleting old receipts would break custody guarantees. Qualification should count file reads, decoded bytes and frame time for increasing historical transfers and multiple campers, alongside crash/reload and concurrent publication correctness. This is not evidence that the user's slot flicker has the same cause.

### MP-017 — Installer rollback leaves the shared patch cache claiming removed hooks exist

Confirmed source failure path. `RebirthHarmonyBootstrap.PatchClassOnce` records successful patch classes in a static `HashSet<Type>` and returns early on subsequent calls. It has no invalidation or live-patch reconciliation. `RebirthNativeSecureAccessPatchInstaller.Install` installs four classes through that helper, then on failure calls `harmony.UnpatchSelf()` and resets its own flag. Test failure at each of the four registration stages, then retry and inspect actual native patch metadata; installer flags and counters are insufficient assertions. ### MP-018 — Hydration equipment moves bypass the original-owner settlement path

### MP-019 — Metabolism recovery ignores backups and accepts structurally wrong stores

Confirmed source failure paths in `RebirthMetabolismStateRepository.EnsureLoaded`. The loader treats a missing primary as a new empty store without inspecting `.bak` or `.tmp`, and loads only the primary. Its writer, `RebirthAtomicXmlFile`, explicitly has a portable replacement path that copies a backup and deletes the primary before moving the replacement. A process interruption in that interval can leave a recoverable backup that the loader ignores, allowing default player state to replace the prior store.

The loader also checks only that an XML root exists. It does not validate the root name/version, silently ignores non-player child elements, and replaces earlier entries on duplicate player IDs. Thus well-formed but wrong-schema input can become an empty or incomplete writable store. The existing detached-candidate publication and generation guard correctly prevent partial publication after a thrown parse error; they do not reject these semantically invalid candidates.

Use strict supported-schema validation with explicit legacy migrations, reject duplicate identities, and distinguish a genuinely new store from recoverable/unknown existing candidates. Preserve failed candidates. Qualify missing primary with valid backup, corrupt primary, wrong root, unsupported version, duplicate player IDs and an interrupted portable replacement. All fixtures must be disposable; no user save was changed.
