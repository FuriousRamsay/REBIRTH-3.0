## UI selection and native effects

Core dispatcher reaches UI tree/find/click/hover/drag/type/scroll paths. Collect enumerates all native LocalPlayerUI copies plus primary/menu, visible window groups and showing groups, deduplicates groups, limits interesting nodes2500. Every visible view's actual bounds projected through that UI's camera; branch visibility checked, but no general scroll clipping filter in tree. Path segments distinguish repeated sibling IDs using #index. Selectors exactpath/id, text/tooltip substring, item/recipe substring by default; exact=1 recipe and exactText supported. Best score chooses exacttext and clickable/ancestor, index overrides. This is heuristic selection, not unambiguous item identity. Coordinate input accepts arbitrary floats/screenscale; invalid scale<=0 normalized, nonfinite coordinates not generally refused.

HTTP Click captures screen point and JSON node, glides, then recollects same path. If an item slot, verifies actual hovered object under current slot view before click, preventing common clipped-grid background false success. It does not verify captured controller/UI instance or original item identity, so same path reused/rebound may be another item/control after yield. Non-slot UI nodes only path existence checked; coordinate-only has no node check. Native GUI click injected through InControl, result reports clicked node/hover/openWindows, not semantic transaction success. Caller must inspect native output/custody.

Type/Scroll endpoints synchronously set XUiC_TextInput.Text, invoke OnChange/reflective OnSubmit and Controller.Scrolled; they deliberately do not synthesize physical typing/wheel. No escaping leads to code execution in bridge itself, but the selected UI callback can mutate save/game state. Endpoint argument/content trust remains local token holder. Owned helper TypeInput/ScrollContextBackpack adds exact player's UI/view/grid and admission rechecks around callbacks; HTTP versions use generic selector and current all-UI catalogue.

## Confirmed unowned HTTP operation cancellation limits

No req.IsAbandoned checks in full UI source. HTTP click can continue its glide and inject click after original request abandonment. DragRoutine sets indefinite mouse hold after3frames, drags12frames, releases, optionally fallback clicks. It has no try/finally around indefinite hold or global modifiers/cursor; post-yield exception/abrupt coroutine cancellation can leave native virtual hold until /release or /stop. Exact failure injection not executed; source cleanup omission established. Click shift/control/alt similarly reset only normal tail, not finally. Concurrent unowned HTTP requests overwrite global cursor/modifiers/holds. Old routine reset can clear newer modifiers; this follows actual shared Input API, no queue-wide operation mutex.

Drag follows destination selector each movement frame to accommodate resizing, but if re-resolution fails it retains old coordinates. It does not revalidate original source item/controller before pickup. strict mode forbids fallback placement click and returns ok=false when still held, HTTP200; ordinary mode can return ok=true with stillHeld nonnull. These are operation/result semantics, not item duplication proof. Do not infer successful transfer from HTTPstatus alone or drop unresolved native cursor custody.

Owned helper variants are materially stronger: exact current player/world, cursor/flags/action ownership, revalidate every nested yield with RunGuarded, verify native cursor pickup if required, release own hold finally, mark unresolved cursor item custody instead of hiding it. TryOwnedInventorySlot matches actual native grid cell with presented player's slot/full owned-item fingerprint/count, rejects clipped/hidden scroll slots and checks live references after discovery. CloseOwned refuses to close while holding item. Those do not automatically protect the separate HTTP click/drag endpoints.

AutoRespawn active by default under bridge pump after6s dead/spawning, tries actual visible spawn buttons and invokes unowned ClickAt; global8s retry. Human environment mode suppresses pump call. Coordinates resolved before paced glide can become stale; no exact spawn context fence. This is accepted launcher automation but can alter a manual death scenario. UI enumeration includes menu/player copies intentionally, with no server authority claim.

## World routing and contrasting request policies

World current-primary dispatcher /pois/gotopoi/clearpoi/lootpoi/raidpoi/enterpoi/routeto/breakdoor. Uses real loaded prefab/blocks/TE features; POI scan excludes decorations/tiny bounds, metadata nearest selection and cached visited IDs. No disposable-save admission in this file. Route and breakdoor physically walk, interact and damage doors via prior Player/Path helpers, may prepare tools/craft in legacy flow. They are mutation routines, not observation.

Explicit /enterpoi is the protected exception: FinishEnter clamps finite maxSeconds1..60 and caps to requesttimeout-5, captures OwnedInputScope with !req.IsAbandoned and realtime deadline, uses RunGuarded over entire nested operation. Invalid world/player/death ends owned scope; deepest disposal cleans input/cursor. Ends409 on incomplete/timeout/refusal, no success if merely reached outside. Existing native target and genuine-tool ownership preserved in Entry/Player owned chain. This is actual bounded cancellation, not just comments.

Other world endpoints Finish simply yield selected routine; no original request propagated to children or abandonment predicate. GoToPoi calls Player.WalkTo with new dummyrequest per leg and can take8legs45s plus detours/instinct waits180s. LootPoi budget1500seconds with nested lockpick180s/transfer/scan waits, only checks captured player dead and specific threats/custody, not original req abandoned. Raid chains travel/entry/combat/loot similarly. Thus ordinary original HTTP60s timeout/504 can leave physical travel, fighting, opening and looting running. Source-confirmed endpoint continuation path, no runtime test. Do not retry or assume timeout rolled back prior native mutations. /stop cancels current movement and releases inputs but does not terminate these outer routines, which can resume/start fresh child walks.

Some loops exceed outer nominal budget because nested child budget is not subtracted; captured alive player reference may remain after global world changes until Unity teardown, no general currentworld fence. Exact wrong-newworld mutation requires native lifetime/order evidence, not proven just by missing check. RaidActive is a5s heartbeat, preventing permanently true flag after stopped routine; WaitForInstincts also beats it. Guard remains enabled; routines explicitly handle awake threats rather than disable instincts. No claim custom combat loops fully qualified here.
