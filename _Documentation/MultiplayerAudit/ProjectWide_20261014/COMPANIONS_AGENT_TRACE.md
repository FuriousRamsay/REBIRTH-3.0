## Confirmed additional defect: remote drone tether state is overwritten with an unsynchronized local map

RebirthDroneLockToPlayer.cs States is a private per-process dictionary keyed by drone entity ID. The only Scripts SetState caller is CompanionService.Process1397, reached by authoritative host/remote command packet. No state replication or client SetState caller exists in located source; unload removes state, world reset clears it. Native access/security lock is explicitly independent and cannot carry this state.

Server DescribeDrone854 serializes DroneLockedToPlayer from server States into the companion snapshot. On remote response, SnapshotService.Receive calls AugmentLocalSnapshot; service491 replaces entry.DroneLockedToPlayer with the client's own dictionary value. It then clears/rebuilds selected drone Commands from that overwritten value. Thus a remote client that just successfully locked its drone receives true from server, replaces it with false, displays LockToPlayer instead of UnlockFromPlayer and permits local Stay selection which server rejects while tethered. Both radial entry206 and radial handler251 also consult the client map, so repeated radial use sends LockToPlayer again rather than unlock. Normal remote UI cannot issue the intended unlock after locking (until state cleared/unload or another explicit command source). Host shares server map and is unaffected. This is source-proved active multiplayer UI/control failure, no runtime reproduction claimed. Recommendation: preserve authoritative snapshot state and provide a bounded world-scoped client projection for radial use, without conflating tether and native access locks.

SetState does not change native OrderState to Follow despite comment saying tether always means Follow. ApplyLockedPosition unconditionally moves when state exists; Stay is only rejected after lock. A Stay drone can therefore be tethered while remaining native Stay, with corresponding HUD/follow-only recall semantics. Treat intended forced-Follow behavior as a contract question; no duplicate finding assigned without accepted design comparison. ApplyLockedPosition itself has no remote/authority guard, but normal remote States is empty, so that is not independent evidence of client-authoritative movement exploit.

## Confirmed additional behavior divergence: host mass recall suppresses all-stationary roster

RequestTeleportFollowers1250 computes HasTeleportTarget. Host branch returns if false; remote branch explicitly sends regardless. HasTeleportTarget1650 onward accepts live drones only when Follow, runtime owned NPC only when Follow and durable active dogs only when persisted Follow. ProcessTeleportFollowers1712 onward intentionally recalls all active owned live drones/NPC/dogs regardless Follow/Stay/Guard and queues unloaded Active dogs regardless order, preserving/reanchoring orders. Consequently a host/SP owner whose entire valid roster is Stay/Guard cannot dispatch the hotkey, while the same remote owner can; adding any qualifying Follow companion makes the host suddenly recall stationary companions too. No lower input gate checks the roster. This is a deterministic inconsistent gate for an active action, independent of unloaded recovery implementation. Recommendation: use the same eligible all-order predicate on both dispatch paths; preserve automatic teleport recall's intentionally Follow-only contract.
