## Findings and qualifications

CONTINUATION-A: confirmed exception-path client availability defect. Client Command230 sets CommandPending=true before Send; Craft185-190 and Cancel192-196 use it without rollback. SetBurning232-235 does the same. If package construction or SendToServer throws, the craft prefix catches/logs the exception, but the session remains pending. Grid transfer, further craft/cancel/fuel and CloseForSwitch then refuse. No command deadline resets that flag; normal terminal reply clears it at102/134, but a request never sent has no such reply. RequestRecycler227 explicitly resets on exception, demonstrating an inconsistent sibling path. Closing/reopening the ordinary window retires the session; do not call this permanent player custody, item loss or duplicate award. A transport exception was not induced in game.

CONTINUATION-B: confirmed switch-close retry weakness, qualified transport condition. RetrySwitchClose259-262 sets SwitchClosePending before Send, with no exception rollback/deadline. Subsequent retries return while that flag is true; only a matching received close response clears it. A send exception or absent response leaves navigation waiting. Explicit ordinary close can release presentation; no evidence this permits mutation replay. Reliable normal request/response delivery is not asserted to fail routinely.

CONTINUATION-C: signed class validation candidate, not promoted. PublicationRecord74 rejects vehicleClass<0. Native entity class identifiers are signed integers and restoration correctly avoids blanket negative rejection (prior restoration trace). This tranche did not prove the current authored Camper class ID is negative, nor compute native hash semantics or run the game; therefore no claim that current Camper publication necessarily fails. Preserve as schema compatibility follow-up rather than confirmed current topology defect.

## Saved publication, refund and reward sequence

PublicationService requires current live mobile binding, stable identity, saved preparation, exact queued saved proof and absence of conflicting terminal receipts. It stages immutable receipt, marks dirty, flushes and checks primary saved XML. Failed flush retains receipt rather than retrying native debit. PublicationRecord canonicalizes path/hash, binds admission and native proof/owner/vehicle, limits64 and rejects duplicate/extra malformed structures; relocated version2 requires exact admission7 removal/install ancestry, while original version1 rejects that relocated schema.

RefundDelivery is original-local-only. It binds original native hold, exact prepared removal/detached plan and saved record. Before native application it saves phase3 with exact before inventory, persists attempted server delivery, then issues one application permit. Partial application is not retried. Saving the after image and owner receipt precedes marking saved and partial training. Confirm requires original permit plus exact after image and native primary witness. Remote refund uses the separate reviewed recovery owner-application path. RefundDeliveryRecord parses canonical twelve-attribute hash ancestry and backpack plan, preserves prepared/attempted/saved phase sequence and caps64; parse success is not mutation authorization. RefundArchiveService requires saved confirmation and owner lease, preflights archive serialization, replaces active chain with immutable archive, flushes and verifies primary archive before releasing reservations/queued authority. Failed saves retain custody.

CompletionService records only original retained successful output capture with saved queued receipt and exact current binding. TrainingPlan derives cycles from admitted original batches or output count, classifies native recipe skill model, bounds multiplier and freezes award inputs into TrainingRecord. No-training recipes explicitly retain a zero award. TrainingRecord restores its frozen model rather than recomputing it on recovery, binds completion/admission hashes, deterministic award receipt and bounded numeric/schema fields. TrainingService saves that plan before TryAwardCraft and checks earned receipt afterward. Definition changes before initial plan creation may affect then-current materialization; this was not classified as a new replay defect.

CompletionArchive requires exact server owner/cache, installed station/native lease, retired job absent from queue and CraftCompleteList, saved native reward receipt1, live matching CVar1, and earned skill receipt when training applies. It correlates a fresh saved vehicle proof, stages archive/removes active records, then flushes/verifies saved archive before releasing reservations/authority. Recovery can reparse archived embedded records; no missing receipt becomes permission to regrant.
