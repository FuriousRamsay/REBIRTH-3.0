## PC-A: declared server capability handshake has no production admission wiring

Source-confirmed reachability gap, not a runtime-observed unauthorized craft. RebirthPersonalCraftAuthorizationService.cs:69 defines a robust server handshake but production source search finds no caller of AuthorizeActivation and no caller of its Install. That class has no HarmonyPatch admission declaration. Its only outside code references are comments, optional diagnostic Attach observers/diagnostic counts, and network request/result types. Full RebirthHarmonyBootstrap confirms targeted class installation and PatchAll disabled. RecipeUnlockPolicyInstallation only installs/qualifies Recipe.IsUnlocked postfix. UiInstaller installs count guards, and ProgressionInstaller installs CompletionService, not the authorization service.

Thus ordinary remote personal activation reaches owner-local native unlock/capability projection and material guards without sending the declared capability admission request. The service's carefully bound original game/world/worldState/peer/user/creation/current-player/epoch/count/tier replay checks cannot be cited as an active barrier. If called, it would permit universal/external/area recipes, evaluate gated personal recipes on server, authenticate request entity/user, expire pending at ten seconds, and replay once only for unchanged intent. Those are dormant implementation semantics.

Impact: server policy enforcement claimed by the service comments is absent at this admission boundary; client inventory/queue authority itself is an accepted architecture and must be preserved. Ordinary local unlock checks still apply, so this is not proof that a normal current locked recipe can be clicked successfully. Qualification needs a delayed/stale owner unlock projection or controlled owner-local projection divergence against current server policy, with local-only ingredients and Remote Resources on/off. Confirm installer reachability and patch ordering, then preserve native owner transaction instead of replacing it with server inventory simulation. Existing NATIVE_TRANSPORT_TRACE's discussion of AuthorizeActivation semantics should be read with this reachability correction.

## Completion custody, retries and persistence

Completion BeforeOutput excludes repairs, workstation groups, managed cooking and unclassified recipes. It snapshots owner's bag+belt count. AfterOutput requires successful output and actual count increase; retry Update observer suppresses a double notice when nested outputStack already advanced outputSerial. Receipt ids use generated session+sequence. Remote messages validate version/direction/sender entity+user and canonical personal recipe/current capability; server recalculates training. Done window/pending limits bound replay. These safeguards do not repair PC-B.

Outbox/peer additions/pending/done are process-memory collections. World start/shutdown/reset clears them; entity replacement drops peer. Outbox expiry is 120 seconds, capped256. An unacknowledged successful item completion has no durable receipt producer to replay after reconnect. SkillAwardReceipts are consulted, but saved receipts only help a receipt that was already awarded; no consumed native queue row recreates a lost completion notice. Credit calls durable TryAwardCraft before recording crafted statistics; a failed first save followed by receipt-already-present retry omits the statistics stage. This parallels MP-015's caller-stage problem, and should be reconciled there rather than implementing a competing award system.
