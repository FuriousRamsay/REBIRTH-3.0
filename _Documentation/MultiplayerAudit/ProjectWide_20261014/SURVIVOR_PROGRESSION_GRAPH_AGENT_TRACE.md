## Confirmed presentation defects

GRAPH-A — authored Discipline recipe cannot display as available even when owned. Overlay.EvaluateCapabilityRequirement supports All/Any/Knowledge/Skill and then emits Unsupported requirement kind with false; no Discipline branch. Actual Config/_Survivor/capabilities.xml:3257–3263 defines rebirthRageCapsule requiring discipline.berserker + Chemistry40 + Medicine30. Real CapabilityService:168–189 supports Discipline: server reads record AcquiredDisciplineIds, remote reads properly scoped owner projection. Thus an otherwise qualified Berserker can have actual recipe allowed while Explorer recipe overlay is Locked/unsupported; even unqualified viewers get unknown discipline detail instead of correct owned/missing status. Advanced disciplines config has grants_enabled=true and authored berserker definition. This is reachable data-contract mismatch; no false crafting admission because Explorer is read-only. Blueprint also unsupported in overlay, but no current authored Blueprint capability hit; do not promote that hypothetical.

GRAPH-B — relationships beyond 24 are omitted before scrolling. UiProjection.Build sets shownIncoming/Outgoing=Math.Min(24,candidates.Count) and emits only those slots; counts beyond become HiddenIncoming/OutgoingCount. Explorer controller scroll count iterates projection.Slots, so maximum scroll reaches only those first24. Focus summary tells player to scroll for more, but omitted candidates never enter slots. Actual crafting_progression.xml has67 distinct primary_skill=skill.gunsmithing recipe IDs (XML attribute selection, not semantic full XML audit). CraftingProgressionRegistry:53–55 loads every recipe element, GetSnapshot107 returns all; GraphRegistry adds recipe->primary Skill RelatedTo for each nonempty primary, independent of craft-award/disabled status. Therefore Gunsmithing incoming degree exceeds24 in a successful current graph build. Search can individually locate omitted recipe nodes, so graph is not erased and no awards lost; relation browsing is incomplete.

HUD-A — summary numerator includes internal reading receipts. Summary provider defines total as progression Knowledge entries excluding LiteratureService.IsInternalReadMarker, but current=owner.KnowledgeIds.Count. Actual owner serialization NetworkService505–514 deliberately publishes all reading receipts, reserving tutorial markers then remaining knowledge/markers. LiteratureService:12–34 identifies literature.read.* and literature.recipe_read.* internal, and RecordRecipeRead:137–145 adds marker after ordinary qualified read. A player reading known recipe references therefore increments summary numerator with receipts that total excludes, potentially completing summary early or showing numerator greater than total. Tracker consumer Render:194–208 consumes provider display for enabled Summary preferences. Skill/Knowledge values are not awarded by provider; source bug is presentation count only. No runtime reproduction.

Search cache key is graph semantic hash + localized Explorer title. Graph semantic hash omits localized/display/name/description content, and title equality cannot prove all translated text unchanged. In-process localization/description reload with same title/hash can retain stale normalized search entries. This is a qualified invalidation limitation, not confirmed ordinary world-transition failure: no relevant live reload event sequence proved. Cache stores old node references; graph Clear itself has no event invalidation; hash changes normally rebuild it.

## HUD providers, persistence and native scope

Providers registry locks default installation/register/get and revisions; four defaults Skill/Attribute/Knowledge/Summary. Registration replaces provider by type. Providers read detached owner snapshot and current definitions; no record mutation. Skill clamps progress, uses definition minimum for absent skill row; attributes use base defaults; synthetic skillknowledge:<skillID> displays owner theory and max; internal reading marker knowledge cannot be explicitly tracked. Summary issue above is separate from track admission. Providers themselves do not check DefinitionsCompatible; normal HUD consumer excerpt also only checks configuredmode + owner.RebirthModeEnabled/HasCharacter. Thus incompatible definitions can still yield local-default or mismatched provider text; exact remote mismatch lifecycle already belongs owner compatibility audit, no new gameplay authority finding.

Store resolves stable local platform identity, normalized GameIO.GetSaveGameDir hash, userdata path RebirthData/HudTracking/worldkey/playerStorageKey.xml. Native GameIO decompiled exact relevant methods using existing Inspect.exe and target Assembly-CSharp: GetSaveGameDir() combines GameWorld/GameName/GameSaveStorageType preferences; overloads append world/name under save root. It is NOT the native SavesLocal GUID method. Two remote servers with same GameWorld/GameName/storage may alias local tracker preferences; current evidence does not establish native remote preference assignment or complete two-server topology, so qualified missing namespace witness, not confirmed collision. Dedicated server does not own presentation selections; these APIs called from owner UI/service. No network destination from saved entries.

Load absent final+bak returns defaults. Syntax XML fallback uses atomic helper. Semantic parse failure separately attempts backup; newer schema explicitly refuses downgrade even when backup older valid. Known row duplicates suppressed; unknown typed entries retained. Historical/missing schema accepted current defaults, malformed bool/int default; normalized order compacts. TrySave clones before normalization and writes current schema; Serialize public normalizes input directly (not pure formatter). Unknown entry/root-extra schema details not all preserved: only modeled entry attrs survive. No gameplay state stored, only enabled/order/type/id and contextual-active-skill toggle. Unbounded local preference rows/strings can allocate/quadratic duplicate-check, already domain trace scope; no remote packet source.

Atomic helper uses per-fullpath process lock, same-directory temp, XmlWriter then stream.Flush(true), parses temp syntax, File.Move on new final or File.Replace with backup; fallback catches unsupported/IO, copies old final->bak, deletes final, moves temp, attempts restore backup if move fails. Fallback is recoverable sequence rather than literal atomic exchange. Invalid current final may rotate into backup on successful next write; helper does not choose gameplay entitlement. PreferenceService refuses writes after load failure/newer schema, preserves outgoing exact-path failed snapshots/retries and debounce; prior full trace. Atomic helper does not alone enforce admission or preserve unknown future schema; public TrySave bypasses service writeability but normal UI uses service. No fault injected. NetworkService GameStarting43 and shutdown151/174 ResetRuntime(true) are concrete lifecycle owners; rendering calls flush due, Explorer close SaveNow.
