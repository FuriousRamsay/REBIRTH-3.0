## State, replay and durable save behavior

TryApplyEvent holds SocialService.Sync, bounds importance/confidence for ordinary finite inputs, deduplicates a global event-ID window of 4096, updates per-(stable NPC, normalized counterparty) relationship, appends bounded memory (256 per NPC), queues relationship mutation and submits social hostility/trust/fear decision signals. GetRelationship returns a clone. Relationship dictionary and number of memory owners have no global retention cap in this service. Faction service separately caps standings at 2048 with recency eviction.

Replay IDs are not fingerprint-bound. A reused Guid for different subject/payload returns success without mutation; no untrusted caller can currently select arbitrary social event IDs through a dedicated packet. Dialogue derives from conversation revision, trade from quote ID, damage producers use fresh random IDs. Their scope prevents promoting the general API weakness into an active remote exploit. Retry after relationship commit but before faction Apply would skip faction on replay because newlyApplied is false; fault atomicity between those domains is a conditional risk, not reproduced.

Social Tick is called every GameUpdate by CommandModApi (:816), then checks nonserver ConnectionManager and decays memory at one-minute intervals using elapsed wall time. High-importance memories do not decay. Decay changes confidence/removes weak memories but does not undo relationship projections. These are existing semantics. Signals are keyed by NPC+signal name, without counterparty; latest published relationship overwrites the NPC-level signal, including on Restore iteration. No actual social signal consumer was found by repository search; native combat uses native FactionManager instead, so actor mixing is not asserted to alter current combat.

SocialPersistenceStore.EnsureLoaded/Save requires nonremote World and ConnectionManager.IsServer=true. Social XML v1/v2 stores relationships, memories, applied events and faction standings in one atomic file. Validation rejects duplicate sections, unknown sections/children, duplicate relationship/replay/faction identities and malformed nonfinite numbers; finite out-of-range values are accepted and Restore does not clamp them. Relationship keys are nonempty/unique but their stable-ID prefix/counterparty structure is not validated. Memory duplicates/counterparty emptiness are not rejected. These are local-file validation limitations, not remote mutation paths.

PersistenceFile.TryLoad primary/backup recovery and rejected-read write protection was fully read. A corrupt store cannot silently become an empty writable store; missing primary+backup and no quarantine/rejection is the only empty initialization. Save captures relationships, memories, replay and factions with separate service lock acquisitions, then SaveAtomic; there is no social revision/dirty gate, and mutation APIs do not save synchronously. Coordinator.EnsureLoaded loads social at :518 and SaveAll commits social at :577 as part of its complete generation. Lifecycle loads on authoritative world start and saves on shutdown (bounded retry). No other SocialPersistence.Save caller was found in Scripts; normal in-session changes rely on coordinated checkpoint/shutdown and do not have a dedicated periodic social serializer. Abrupt process loss before checkpoint may lose recent social changes; no crash durability guarantee is claimed.

Successful coordinated shutdown calls ResetWorldScopedState, which clears social and faction services (:488,:490), replication service (:502), dialogue sessions and other volatile state only after save success. On save failure it retains backing services, which is intentional retry protection. SocialPersistence.Reset(true) only clears loaded/source; it does not save or clear social/faction state.

## Confirmed finding: exceptional cross-save social contamination

Lifecycle.PrepareWorldScope detects an unexpected World reference or save-directory change, invokes ResetUnexpectedWorldScopedState (:425), then transitions to the new scope. That limited reset calls coordinator.ResetForUnexpectedWorldBoundary but omits SocialService.ResetForWorldChange, FactionGameplayService.ResetForWorldChange and ReplicationPerformanceService.ResetForWorldChange. Coordinator clears SocialPersistence.loaded with Reset(true) (:799); it does not clear those service dictionaries. SocialPersistence.EnsureLoaded (:33) on a genuinely new save with no social primary/backup sets loaded=true and returns without Restore or clearing service state. Therefore prior save relationships, memories, replay IDs and faction standings survive into the fresh save and a later Save serializes them into that new save.

Preconditions: previous world retained social data and expected shutdown did not finish (or an explicit exceptional world switch); next save has no stored social state. Normal successful shutdown already clears the services, and a valid next-save social XML restores/replaces the dictionaries. Corrupt next-save file remains write-protected; it does not become a writable empty file. This distinction narrows the finding to the actual exceptional path. No runtime reproduction performed. This is separate from the already documented observation that Reset(true) performs no write: the defect is failure to clear the backing service state before empty initialization. Correction should preserve failed-save retry within the old world while discarding/rebinding old social state at a proven new-world boundary; no implementation or scope redesign authorized here.

## Confirmed source gap: relationship replication adapter never installed

SocialService.TryApplyEvent (:125) queues each social delta into ReplicationPerformanceService.QueueRelationship but ignores failed admission. Full-read replication service defaults to NullReplicationDispatchAdapter whose ApplyRelationshipMutation always returns false. Repository-wide search for IRebirthNpcReplicationDispatchAdapter and RegisterAdapter found only that interface/default and registration method; no concrete dispatch implementation or production RegisterAdapter caller. FlushRelationships (run once per minute by Social Tick) therefore leaves its head pending. RelationshipBatcher subsection was fully read: 4096 source cap, 128 items per source; once admission fills for an NPC, subsequent events update authoritative relationship/persisted replay but fail relationship queue admission, with no retry in SocialService.

This proves the advertised relationship batch push path is not connected by current source. It does not prove remote dialogue disposition is stale: that is recomputed on server and returned in the interaction response. It also does not prove native FactionManager changes should occur: no bridge from custom faction standings to native faction manager is implemented here. Scope/required client social surface must be checked before proposing a new protocol. Parent should classify as an integration gap, not silently enable or invent client/native social behavior. No runtime delivery claim made.
