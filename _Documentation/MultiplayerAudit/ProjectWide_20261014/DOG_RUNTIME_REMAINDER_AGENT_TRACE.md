## Auto-loot custody and residual risks (ordinary UI path dormant)

TryInterceptSlot sends only source position/slot, expected type/count, authenticated player/user and operation GUID. ProcessPackage requires ToServer, nonremote world, ValidEntityIdForSender and ValidUserIdForSender. ProcessServer resolves persistent primary identity and server TEFeatureStorage, exact position/slot, authenticated player's native single/shared loot lock, collect+30m distance and current eligible server item/type/count. It clones the authoritative item; the client cannot supply serialized awarded contents.

Target selection requires active aggregate dog owned by that persistent owner, live enabled available runtime entity, whole-stack capacity and nonzero inventory revision. It does not check native bag busy state or dog-owner distance. Source is emptied/modified before insertion. TryAddAtRevision stages a snapshot, requires expected inventory revision, rejects insufficient total capacity before CommitWorkingSlots, then atomically publishes the aggregate revision. A failed insert restores the full source if still empty; if occupied, full compensation goes to server player bag/inventory or drop. This is NOT a confirmed partial-insert duplication: the revision-aware insertion does not publish partial capacity plans. The legacy nonrevision TryAdd does allow partial commit, but its legacy routing wrapper has no release caller here.

There is no persisted operation receipt or server GUID dedup table. Replayed request cannot consume the original empty slot; replacement same type/count would be a new server stack under the still-valid native lock. Pending UI requests have no timeout/close cancellation and key only position+slot; missing response suppresses subsequent eligible clicks there until response or registered world reset. This is a source-level liveness failure conditional on absent response, not a demonstrated normal transport loss. Response removes pending before current UI validation; it may intentionally abandon visual handling after close. Both success mirror clearing and fallback use type/count rather than full item fingerprint or container incarnation: delayed same-type/count replacement handling remains a timing hypothesis, requiring exact native sync ordering. No claim that authoritative loot duplication was reproduced.

Native bag edits can overlap direct authenticated auto-loot packet mutation because target selection does not honor StorageService.IsOpenServer; canonical revision prevents stale overwrite, but rejected native mirror restoration cannot undo player-side transfers. Need precise native UI/packet interleaving before promoting inventory loss/duplication. Ordinary auto-loot UI emission remains absent as above.
