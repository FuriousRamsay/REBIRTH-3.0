## Authority and native integration

Pack requests require an authenticated player ID and authoritative world. Eligibility checks player placement, no current tile access, claim membership, secure access, undamaged root block, storage target with count one and six-metre distance. Local and remote requests converge on Pack. The actual item grant/removal reuses native PickupBlockServer; retain this native architecture.

Pack captures native item serialization plus dimensions, categories, activation, exclusions and name. It writes a token file, sends a separate metadata packet (or stores locally), empties storage, and calls native pickup. Exception rollback restores contents only when the same tile still exists. Successful return clears auxiliary records without inspecting a native removal postimage. Exact native silent-rejection behavior remains to be traced before classifying that as a defect.

The metadata inbox is world-reference scoped, keyed only by position, expires after 30 seconds and is removed before attaching metadata. Client pickup consumes it when creating the granted ItemValue. No original pickup operation or source identity correlates this pair. Native reliable ordering must be checked before claiming routine packet reordering; delayed grants and same-position reuse remain required test cases. Inventory grant then follows existing stacking/hand/backpack/drop behavior.

## Restoration and recovery

Local placement captures held metadata before placement. Remote native SetBlock processing captures matching held metadata and newly empty positions; its postfix attempts restoration after the native handler. Actual sender validation belongs to the native path and still requires inspection; do not substitute comments for proof.

Restore requires an issued token, matching block, player-placed empty storage, no user accessing, secure access and eight-metre range. It validates dimensions and native item payload. It then renames the token file to `.placed` BEFORE Resize, item publication, SetModified and settings restoration. A failure or process stop after rename leaves a consumed token with no automatic continuation in this component. The retained file preserves bytes but does not establish successful world publication. Subsequent Restore calls return when the original file is absent. This is MP-022.

The detached camper API uses the same receipt namespace but separate prepare/publish/read/consume calls. Its caller settlement must be traced independently; do not assume the world-placement finding proves camper transfer failure.
