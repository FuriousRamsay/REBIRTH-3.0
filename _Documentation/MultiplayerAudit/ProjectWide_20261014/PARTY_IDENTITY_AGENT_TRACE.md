## Confirmed PARTY-A: unresolved saved metadata remains writable

Service OnGameStarting resets Personal/Groups/runtime links/revision, enables serverAuthority from native event, then calls Load. Load uses groups.xml, attempts backup only when primary cannot be parsed by AtomicXml.TryLoad. If both fail, it logs and returns. A parseable wrong root/unsupported schema throws only inside semantic-validation try, is logged and returns WITHOUT trying a usable semantic backup. There is no loaded/writable/recovery-required flag preventing later edits/party resolution from publishing the empty initialized dictionaries.

A subsequent valid native party creation through AddPlayer postfix creates a GroupRecord, dirty=true, then SaveIfDirty atomically publishes a new incomplete snapshot over the unresolved file. A valid solo group-name edit likewise makes dirty and writes. Failure condition is concrete unreadable/unsupported existing groups.xml, not absence of any saved file. Current user's data was not read/injected and no corruption claimed. Atomic publication helper preserves a prior byte candidate when feasible but does not make the newly incomplete state valid; later saves can rotate that backup. Metadata affected is group/solo names, colors, leader/member reconciliation, not native party membership/items.

Load additionally silently takes first4096 personal records/2048 groups/eight member keys, skips empty keys/IDs, and overwrites duplicate keys/IDs. Runtime dictionaries have no corresponding admission bound and histories are retained. A subsequent save after a larger valid file discards unvisited records. This is a source format-preservation limit; reaching those counts during ordinary server operation was not demonstrated. ParseInt/ParseLong accept malformed/missing numeric fields as0, then normalize; unsupported root/schema is rejected but still writable as above. No full semantic backup validation occurs before state publication.

## Confirmed PARTY-B: settled broadcasts can reuse a pre-settlement party snapshot

BuildSnapshot469–499 cache key is global metadata revision plus world player entity-ID roster signature. It does not encode player.Party, LeaderIndex, membership or local permissions. Cache hit returns before TryResolve/RefreshPartyRecord. RemovePlayer postfix calls OnPartyChanged -> refresh metadata -> SaveIfDirty -> BroadcastSnapshot -> BuildSnapshot.

Exact native Party.RemovePlayer removes the actor from MemberList but does not clear actor.Party. Native Party.ServerHandleLeaveParty then calls player.LeaveParty, adjusts LeaderIndex or SetLeader and sends native party packet. Exact native EntityPlayer.LeaveParty clears Party and invokes PartyLeave event. REBIRTH has no PartyLeave observer in this service. Its ServerHandleLeaveParty postfix merely BroadcastSnapshot; it does not invalidate cachedSnapshot or resolve actual party state.

Concrete normal trigger: at least three players in a party, a nonleader after the leader in the member list voluntarily leaves, leaving at least two members. The RemovePlayer postfix snapshots the leaving player's still-nonnull Party, so that player's row is still grouped. Native subsequently clears Party and SetLeader(existing leader) runs; its REBIRTH OnPartyChanged finds leader/member metadata unchanged from RemovePlayer's already-refreshed record, hence no revision increment. World player roster is unchanged by voluntary party leave. Both SetLeader broadcast and settled leave broadcast therefore can return the cached row with old IsParty/GroupId/name/CanEdit instead of solo identity. Force RequestSnapshot bypasses no cache: it forces delivery, not rebuilding. Opening Players can thus redisplay the stale state until a later uncached resolve/metadata mutation or roster change invalidates cache.

Transferred-leader variation: leader at nonzero member index leaves or disconnects. RemovePlayer postfix sees LeaderIndex still referring to the shifted member or out of range, refreshes group record to wrong/empty leader and may seed that transient leader's solo metadata. Native departing-leader branch directly sets LeaderIndex=0, rather than invoking patched SetLeader. Settled BroadcastSnapshot can reuse the pre-reset cache, so CanEdit/group leader projection stays wrong. Native KickPlayer clears departing Party before its postfix, but ServerHandleKickParty still directly resets leader index afterwards and this service has no settled-kick wrapper, leaving the leader-permission variant. No runtime reproduction occurred. This is metadata/projection consistency and temporary personal-seed pollution; authoritative ProcessServerRequest calls TryResolve afresh and checks current native party leader, so stale client CanEdit does NOT by itself authorize a nonleader edit.

Disconnect differs from voluntary leave: later actual world player removal changes roster signature, so a subsequent snapshot rebuild can self-correct. Do not claim permanent stale disconnected membership. Voluntary leave keeps all world players, exposing the cache miss in settled mutation handling directly. Correction scope is coherent cache invalidation/re-resolution after native settlement, not replacement of native party ownership.

## Service installation, ownership and lifecycle

Install patches native Party.AddPlayer/RemovePlayer/KickPlayer/SetLeader/Disband, settled Leave/Disconnect, PartyManager.RemoveParty and GameManager.SaveWorld, then registers GameStarting/Joined/Spawned/WorldShuttingDown/GameShutdown and marks installed. SurvivorInstaller115 actually calls through RunStep, after network/progression and before UI integration. Class once helpers protect repeated successful class patches; a failure during later event registration could leave earlier handlers/classes registered without installed, existing partial-install family. No game run verified handler cardinality.

Authority is event-derived serverAuthority plus current Rebirth mode. Remote clients ResetRuntime(false), never own SaveIfDirty or native party reconciliation. Host/dedicated both load world save/RebirthData/PartyIdentity/groups.xml; host also receives client projection directly, dedicated broadcasts to clients. OnJoined/Spawned remember real ClientInfo identity; spawn resolves live player then sends snapshot. Both shutdown handlers SaveIfDirty before clearing runtime/serverAuthority and client projection. Save failure leaves dirty=true for later bounded world save/edit/shutdown retry, but shutdown still resets after failed write, so there is no durable pending metadata log. ProcessServerRequest reports 'group identity updated' and broadcasts even if SaveIfDirty returned false; this is successful volatile mutation, not verified durable completion.

Schema1 persistence records personal stable-key seed and retained group GUID/name/color/leader/member-key sets/revisions. RuntimePartyGroups maps native PartyID to retained group GUID only within session. Add/leader/member changes refresh record and revision under Sync; leaving/disband removes runtime association but retains history. Reload chooses latest group led by current leader, then strongest membership overlap requiring>=2 matches, then creates a group seeded from leader's personal preferences. Ownership follows verified native leader; metadata is not membership authority. Changing leader seeds that leader's personal name/color for later disband/reform. Underlying native Party caps8 members; serialized member8 cap matches this actual native limit.

Save serializes under Sync, writes outside Sync with atomic helper, then clears dirty under Sync. A concurrent mutation during write could be cleared without being serialized; actual native dispatcher/event paths reviewed are synchronous main-thread execution, and no off-thread caller demonstrated. Treat concurrency concern as unproven. Existing helper portable replacement interruption behavior remains shared persistence findings, not a new group-only atomicity claim.

## Stable identity: remote/unknown/disconnected scope

RebirthStablePlayerIdentity147 FULL. Canonical durable identity derives from ClientInfo.InternalId.CombinedString or server-owned PersistentPlayerData.PrimaryId.CombinedString; filename key is SHA256 of UTF8. Remember caches by runtime entityID. TryResolveServerEntity first uses cache, then native persistent-player mapping for that entityID. Only actual EntityPlayerLocal has local-platform fallback before native mapping exists. An unknown remote EntityPlayer does not fall back to the host identity: resolver returns false and its snapshot row/profile is omitted/unavailable. Offline profile target lookup uses world.GetEntity; no fabricated profile for a disconnected player lacking live entity.

PersistentPlayer helper requires main thread+repository server authority and does not register stale entity alias. General TryResolveServerEntity itself does not enforce current world/object/connection identity; call sites here supply current world entities from native party/world/request routes. Same-world ID reuse/stale object manually invoking helper would require its own evidence; no such native reachable reuse established. ByEntityId cache is reset on native GameStarting and world/game teardown through full-read SurvivorPersistenceLifecycle115. Disconnect FlushClient remembers the outgoing ClientInfo and saves actor data but does not evict identity cache; retained alias is session-local, not an offline ownership grant. It supports native still-referenced disconnect party members. A replacement connection Remember overwrites same entityID with its own server-derived identity.

Unknown leader reconciliation has a conditional weakness: ResolvePartyNoLock sets leaderKey empty if native leader identity cannot resolve, then searches Groups for LeaderStableKey==empty; Refresh can persist empty leader. Two unrelated unresolved-leader parties could select the same retained empty-key record before overlap logic. This does NOT mean unknown remote identity maps to host identity or permits edit; TryResolve still first requires requester/member stable identity and edit checks actual native leader. No ordinary native path with unresolved persistent/ClientInfo identity after joined/spawned proved here; document as conditional metadata association risk. Do not elevate to confirmed remote identity hijack.

## Native transport trust and actual package registration

Installed native NetPackageManager static constructor discovers NetPackage subclasses through ReflectionHelpers.FindTypesImplementingBase and indexes type names. StartServer assigns known IDs; StartClient resets base mappings; IdMappingsReceived matches server type names and disconnects on unknown type. Thus these non-Debug compiled package classes use actual native registration/discovery, not an absent custom Register call. Native ParsePackage assigns Sender from transport ClientInfo BEFORE payload read; requester cannot serialize Sender in these REBIRTH packets.

Native ConnectionManager server Update dispatches each connected client's queue with ToClient disallowed and actual ClientInfo, and rejects packages before loginDone unless AllowedBeforeAuth. Client dispatches only connectionToServer queues with ToServer disallowed. ValidEntityIdForSender on server compares supplied actorID to Sender.entityId; allowAttached is false here. It is not a stable-ID string comparison, nor a complete current-connection/object/world-generation guard. Immediate party/public handlers resolve actor/target from supplied current World, reducing stale entity-reference exposure. Prior native disconnect evidence clears old connectionToServer before cleanup; absence of custom epoch alone does not prove old-server replay into a new session. No native transport redesign proposed.

Party request ToServer validates world nonremote, protocol2 and ValidEntityIdForSender, resolves current player and delegates server service. ProcessServerRequest validates authority/mode/TryResolve/current.CanEdit and resolves server stable identity, normalizes BBCode/control chars/name32 and color (palette8 or encoded RGB), then mutates own personal seed and actual player's Party record. There is no arbitrary GroupId/leader/membership in payload. Invalid operation codes currently route to snapshot request, not edit. knownRevision is sent but not used to short-circuit remote snapshot; force is delivery preference, not freshness check. No cooldown/rate limit in this endpoint; expensive request flood not measured.

Snapshot ToClient rows<=128, name32/groupID64 bound after BinaryReader.ReadString, normalized color, protocol2 and nondecreasing revision. Client snapshot map is cloned by entityID, so callers do not receive mutable canonical dictionary. Reset clears snapshot/dictionary; changed event listeners unsubscribe normal UI close. Snapshot ProcessPackage itself does not recheck world.IsRemote, but native direction gate forbids client-authored ToClient processing on server. Do not infer client permission forgery from missing redundant gate. Oversize strings allocate before truncation; actual native packet-size budget not fully traced here, so no unbounded-memory exploit claim.

## Public profile request and lifecycle closure

Prior FULL PublicProfile66 and Players676 reads reused. Server handler requires nonremote world/current Rebirth mode and validated requesterID; target resolved as EntityPlayer from current world. FromServer uses stable resolver then CaptureOwnerState. Scoped CaptureOwnerState416 onward reads canonical repository record, returns RecoveryRequired/absent state when not usable, and projects current authoritative origin/progression. PublicProfile.Build invokes existing snapshot builder and copies only background ID/display/identity plus top4 practical skills/icons. Entire private owner snapshot is not sent. Public fields are intentional public UI; no distance/ally requirement is implemented or inferred necessary.

Host details builds directly from server; remote owner's own view uses local owner projection; other live targets request every5s. Server replies attached to authenticated requester; ToClient handler requires remote World and raises local Received. UI receives only matching selected entityID, unsubscribes/clears on close; no custom operation/world token is present, so newer/out-of-order same-target replies can replace display values (read-only eventual consistency). Offline PPD remains selectable but no live target means no authoritative public build; UI displays unavailable. No profile read grants player resources/progression. Native current request identity, not client-provided stableStorageKey, controls capture lookup.

GetLength response estimate omits BackgroundId and allows strings read without explicit REBIRTH bounds. Native NetPackage base has no GetLength virtual contract in the scoped type read; this estimate alone is not established allocation/framing authority. No truncation defect assigned without actual native serializer caller proof. SnapshotBuilder complete internals and repository recovery validation remain their prior/parallel progression scope, not re-certified by this narrow projection trace.
