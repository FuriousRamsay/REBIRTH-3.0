## Replay, repeated reward and split-domain failure limits

Outer profession Committed and inner base ReplayIds each retain 8192 GUIDs. Inner base replay is persisted with XP; outer profession Committed is process/world runtime only. Two concurrent Commit calls can both pass the outer precheck, but Award serializes under its lock and the second sees base replay, so there is no double accepted XP solely from that unlocked precheck. After reload, the base persisted GUID still returns Duplicate. IDs are globally keyed, not fingerprint-bound to NPC/track/payload; a reused ID with different payload is suppressed rather than authorized as new work. Caller-derived WorkId salt prevents ordinary repeated terminal-work awards. After bounded replay eviction, the service alone cannot prove an ancient ID was used, but actual replayability needs a production caller bypassing terminal work identity; not established.

Award mutates XP/replay/dirty before telemetry and replication publication, and profession Commit updates its own cache/advanced counts only after Award returns Accepted. Exception in post-XP publication can therefore leave XP accepted without outer profession/mentorship/certification bookkeeping; retry sees base Duplicate and cannot repair those follow-on effects. Likewise an exception between outer cache commitment and advanced callbacks can leave incomplete advanced state. This is a source-confirmed fault boundary, conditional on those external calls failing, not a reproduced current reward loss. Persistence is not a transaction across XP and advanced sidecars except coordinated generation save. Do not refund XP or replay outcomes speculatively.

Advanced OnProfessionAwardAccepted accepts outcomeId but never deduplicates it, simply increments per-profession completed outcomes (unchecked int) and evaluates certifications/specialization. Its sole production caller is accepted profession Commit; other calls are explicit qualification. Thus the missing check is an API limitation guarded by current caller replay, not an active duplicate-reward finding. At max XP, Award returns AtMaximum before recording ID; profession Commit does not increment advanced completed outcomes. Whether certification progress should continue at cap is a design question, not an approved behavioral change.

## Persistence and exceptional reset extensions

Base progression XML schema 1–2 carries records, per-entry last award and global replay GUIDs. Import clamps known-track XP to curve maximum and recomputes level; unknown track entries are retained without normalization. Parser defaults malformed integer attributes to zero and skips malformed IDs, accepts duplicate NPC/entry records with later-record overwrite and unknown children. Advanced XML schema 1 similarly accepts unvalidated enum casts, certification/specialization strings, counts and finite/nonfinite ranges; Import revalidates sessions, but does not validate all record semantics. These are local saved-state preservation/validation limitations, not arbitrary remote mutation paths.

Both stores use temporary XmlWriter files then File.Copy(primary,backup,true), File.Delete(primary), File.Move(temp,primary). This is not the shared flushed/verified atomic replacement writer: failure after deleting primary leaves missing primary with backup/temp; subsequent loads can use backup, but crash/durability and complete checkpoint rollback remain parent dependencies. Existing blocked-read guards protect failed primary+backup reads, yet missing primary+backup branches call AssertWritable (which only consults current-process rejected reads), not CanInitializeEmpty/quarantine checks.
