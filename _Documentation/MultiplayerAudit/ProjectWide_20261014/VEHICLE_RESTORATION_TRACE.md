## Identity index and recovery observation

The Carriers map is explicitly diagnostic and last-writer-wins. Recovery does not trust it: TryLocateTransferTarget scans both block/entity indexes, requires exactly one matching assembly ID, matches block coordinates or entity carrier, and returns a clone. Duplicate loaded identities therefore refuse recovery instead of selecting one. Stale index entries could cause conservative refusal; native unload tracing is needed to establish that case.

TransferResolver additionally requires an authoritative current world and current session, re-reads live block/entity state, compares complete serialized snapshots against indexed state, and rechecks world/session before returning. Its comment correctly distinguishes observation from a disk-save witness. Do not treat successful resolver lookup as durable item-transfer completion.

RegisterEntity writes assembly metadata into the native vehicle item before publishing index state. CommitEntity validates size, increments revision, compiles performance, registers, then requests native sync flag 4; native sync/save and caller failure recovery still need tracing. ModAPI clears the index at GameStarting, deliberately retains it through shutdown for native vehicles.dat serialization, and clears transient requests separately. Verify actual native shutdown ordering before proposing earlier cleanup. Its initialized flag is set before installer calls, extending MP-013's retry vulnerability subject to installer failure propagation review.

## Native packet admission and size boundary

Read the complete installed NetPackageVehicleDataSync decompilation. It authenticates senderId using ValidEntityIdForSender, resolves vehicleId, invokes ReadSyncData, catches/logs read exceptions, and on server rebuilds a reply using GetSyncFlagsReplicated. That mask is 0xC007, including item flag 4. It does not itself require vehicle ownership/attachment in this body. This is native behavior under the accepted trusted installed-client architecture, not grounds for a global server-only inventory rewrite or an unsupported anti-cheat claim.

Restoration's ReadSyncData postfix does not receive senderId and restores metadata without comparing assembly revision/transfer context. Camper pending-transfer and maintenance guards can suppress flags 4/8 while their respective holds exist; they are conditional safeguards, not universal restoration freshness checks. Trace ordinary StopUIInteraction/client flag-4 producers and pending restoration transactions before diagnosing an actual stale overwrite.

The native packet writes entityData.Length as ushort but writes the full stream afterward; read consumes the ushort-sized length. AssemblySerializer allows 262144 decoded bytes and up to 349528 Base64 characters, which can exceed that native envelope even before other ItemValue fields. This is a source-confirmed incompatible upper-bound allowance, with actual reachable content size still pending. Add exact full ItemStack/sync envelope sizing at publication/admission rather than assuming the persistence maximum fits the wire. Tests should cover just-below/at/above 65535 total native payload bytes, including other metadata and flags. Do not claim current vehicles hit this limit; no payload-size or runtime test ran.

Potential failed-read behavior also matters: native ProcessPackage catches a partial read exception and still considers replication afterward. Preserve this evidence when designing failed assembly publication handling; a logged error alone is not a clean rollback.
