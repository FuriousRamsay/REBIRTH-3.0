## Native owner custody and authority

The client first freezes its original exact held-slot value and publishes normal NetPackagePlayerData before requesting a transfer. Server admission authenticates the sender/entity/character/world and physical sink target. For a remote owner, the server waits for the authenticated final native owner file to contain the exact offered held-slot native value/count and validates the native held index and owned toolbelt capacity. A local owner is checked directly. Offered bytes cannot author a reservoir result: the authority derives the vessel conversion, delta, current tank before/after values and revision itself.

Before any vessel mutation, the authority persists an immutable `RebirthCamperTransferJournal` record under `REBIRTH/CamperSinkTransfers`. The bounded frame includes operation/camper/world/owner/creation/held slot, complete original/result native item images, reservoir before/after millilitres and expected revision. One camper accepts only one unresolved sink receipt. Repeated/replayed operation identifiers cannot acquire another mutation or reservoir change.

Only the native owner can apply the server-authored frame. It validates stable owner and character/world, exact original held-slot image, owned slot, original request/camper identity, and receipt phase. It marks/publishes native receipt phase2 before its sole permitted SetItem on that original slot, verifies the exact result, then marks/publishes phase1. A duplicate phase1 only republishes acknowledgement. A resumed phase2 accepts only the exact original or result value; it never overwrites unrelated inventory state. No bag/cursor restoration, inventory-array replacement or source synthesis is performed.

As in existing RemoteOwnerApplication, durable native receipt1 is the completed owner publication proof. Subsequent legitimate movement of the converted vessel after reconnect cannot undo the paid proof. The server reads that receipt from the authenticated final native player file before advancing its journal to Uncertain, then applies the exact tank delta once. An already-matching after revision/amount is accepted during recovery. It requests native vehicle saving and requires the SavedVehicle witness before marking Applied and releasing the owner hold. A crash between player conversion and vehicle publication retains the immutable journal; the same owner reconnecting/focusing the sink rebinds it. A persisted receipt2 can resume its exact original/result slot, and receipt1 can settle without a second debit. A server Prepared receipt disconnected before the owner ever persisted receipt2 has no automatic resume authority: the owner has no saved attempted receipt and its original local request is gone. That case remains explicitly unresolved and blocks new sink transfers; it must not be described as complete automatic reconnect recovery. The code does not recreate a phase0 request or silently debit an owner after reconnect.

During custody, new native primary/secondary held actions, toolbelt mutation, item drag/drop/swap/preferred moves, action-menu crafting/use/equip/scrap/trade actions and dropping the held item are blocked at their existing admission points. Existing resource-use gates include the sink hold, and Backpack/Gear/Energy/native camper payment admissions cannot acquire competing custody. Resume refuses an existing unrelated owner reservation. The only permitted mutation is the exact native original-slot conversion. These guards are sink-owned scoped Harmony patches; they do not change existing feature receipt formats or reservation records.

## Compatibility, performance and limitations

Native owner inventory trust is preserved: server cannot safely replace client inventory replicas and does not attempt to do so. Dedicated/listen-server requests use the same authenticated owner-file witness and server-authored result as the local path. Actual runtime multiplayer acceptance has not been established here.

Receipts and metadata are additive. No old save format, persistent option ID, station module layout, energy state or network package payload is modified. The new versioned sink packets are bounded and direction-specific. A separate authoritative metadata guard prevents native client vehicle snapshots from changing water custody. Existing saved-owner codec read patches installed by the Energy implementation are a dependency; they preserve complete native held item images during remote owner-file reads.

Pending or inconsistent receipts fail closed rather than deleting vessels or repeating a debit. A disconnected client, failed native save, invalid saved owner data, character change or altered original slot can retain an unresolved transfer and temporarily prevent further sink use; the immutable receipt remains for the original owner/reconciliation. Source-level inspection cannot establish which native failure modes occur in play. The feature does not invent rollback/reconstruction of an unrelated inventory to conceal such an uncertainty. Completed receipts are retained in the existing journal style.

Client queries and local recovery scans are rate-limited to one second per focused sink. HUD binding observation is 5 Hz; pending native-save proof is checked at 2 Hz. No broad world scans, per-frame disk scans or reflection occur. Reflection is restricted to cached Harmony target discovery at installation using existing native methods.

## Remote world and reconnect review

`WorldScope` now supplies the native connected `GamePrefs.GameGuidClient` for remote worlds and the authoritative `worldState.Guid` for local/server worlds. Primary requests, focused queries, Apply, ReceiveReply, server admission/recovery and server replies share that helper. Exact retained native `World.LoadWorld` constructs WorldState for both sides but loads/generates the authoritative main.ttw GUID only in the server branch; `World.Guid` merely returns that WorldState value. Native GameManager separately uses GameGuidClient to identify remote saves. This evidence does not establish that every remote WorldState GUID is always wrong; it establishes that the connected-game identity is the proper remote binding and matches existing REBIRTH mode input paths.

Reconnect authority remains the immutable frame's stable owner ID/key, character creation and world/camper identity, rather than the original transient actor entity ID. The server rebinds a retained operation to the newly authenticated owner entity/connection. The local side now forgets only a detached old player object (no longer the current primary/current entity), permitting its saved receipt2 to acquire the exact original custody on the replacement player. It does not forget an active current owner's hold to admit another operation. Apply also requires the actual current vehicle identity, and a received apply frame must match its outer reply's operation, camper and world.

A delayed settlement reply may contain an older presentation revision than a newer gauge query. The amount projection remains monotonic, but that older revision no longer discards an exact operation's settlement acknowledgement and strands its owner hold. This changes acknowledgement processing, not reservoir revision ordering or amount authority.
